# Build Log

Per the capstone's ground rules: "AI-assisted building is encouraged — and
owned... You must be able to explain any 2–3 lines of your code that the
evaluator picks. 'The AI wrote it' is not an answer."

This log is an honest account of how this repository was produced, so it

## How this was built

The full application — architecture, migrations, every route/controller/
service/repository, the widget loader script, the Jest test suite, Docker
setup, and this documentation — was generated by Claude (Anthropic), acting
as an AI pair-programmer, in direct response to the capstone brief PDF.
Nothing here is a template filled in by hand afterward; it was written
file-by-file against the brief's specific requirements (Section 6) and
verified by actually running it, not just written and assumed correct.

## What was actually verified, not just written

During the build, the running server (SQLite mode) was exercised directly
with `curl` and with the Jest suite, and the following was confirmed
against real output (not just read from the code):

- Migrations run clean on a fresh SQLite db and on the schema Postgres will
  see (same Knex migrations, both dialects).
- A full register → create-widget → cross-tenant-404 → own-tenant-200 flow,
  via real HTTP requests with two separate tenants.
- `POST /api/public/submissions` happy path, missing-field → 400,
  oversized-body → 413, malformed-JSON → 400, unknown-widget → 404.
- A honeypot-filled submission returns 200 but is not written to the
  `submissions` table.
- A burst of requests against a lowered `RATE_LIMIT_PER_IP_MAX` returns
  exactly the expected 201/201/.../429/429 sequence.
- All three geo-fallback branches (A up · A down→B · both down) against the
  deterministic mock providers, confirmed via the response body and the
  stored row's `geo_provider` column.
- `FORCE_EMAIL_FAILURE=true` still returns `201` for the submission, and
  after the retry backoff, a row appears in `failed_jobs`.
- The full Jest suite (23 tests / 7 files) passing together, not
  cherry-picked individually.

The exact commands and output used for this are pasted into `EVIDENCE.md` —
that file is real, run output, not fabricated.

## Design decisions worth knowing the reasoning for

- **Knex over a heavier ORM (e.g. Prisma):** avoids a binary-download step
  at install time and keeps the same query code working on both SQLite
  (quick start) and Postgres (docker-compose) with no dialect branches in
  application code.
- **JSON fields stored as TEXT, serialized in the repository layer:**
  SQLite has no native JSON column type; storing as TEXT and
  `JSON.parse`/`stringify` in one place (`widget.repo.js`, `submission.repo.js`)
  keeps every other file working with real objects.
- **In-process rate limiter and job queue instead of Redis/BullMQ:** the
  brief promises a $0, no-extra-services stack; both are written behind a
  narrow interface so swapping in Redis-backed versions later is a
  single-file change. This is written up as the explicit non-goal in
  `docs/DESIGN.md`.
- **`GEO_MODE=mock` as the default:** the brief explicitly asks for a
  deterministic fallback-chain proof, not a proof that depends on two free
  third-party APIs being reachable at grading time.
- **Honeypot returns a fake `200`, not a `4xx`:** telling a bot its
  submission was rejected teaches it what to avoid; a convincing-looking
  success gives it no signal at all.

## Where the AI got something wrong, caught by actually testing it

The first version of `knexfile.js` resolved the SQLite file path with
`path.resolve()` but never ensured the containing `data/` directory
existed. That directory is git-ignored (see `.gitignore`), so it's present
on the machine that built this repo but **absent on a fresh clone** — the
first `npm run migrate` on a clean checkout would have failed with
`Cannot open database because the directory does not exist`, directly
violating Section 11's "a stranger can run it" requirement.

This was only caught by explicitly simulating a stranger's first run — copying
the repo to a clean directory, deleting `node_modules/` and `data/`, and
running `npm install && npm run migrate` from scratch. It did not show up
in any test run against the machine that had been building the app all
along, because `data/` already existed there from earlier manual testing.
Fixed by having `knexfile.js` create the directory (`fs.mkdirSync(...,
{ recursive: true })`) before handing the path to the SQLite driver — see
the comment in that file for the full reasoning.

The lesson generalizes: **passing tests are not the same evidence as a
clean-machine run**, and it's why `EVIDENCE.md`'s Docker/Postgres item is
still marked for you to verify yourself rather than assumed to work by
analogy with the SQLite path.



This log being honest cuts both ways — here's what wasn't (and can't be)
done by the AI, and is on you before you submit:

1. **Read the code.** The evaluator will point at 2–3 lines and ask you to
   explain them. Start with `src/controllers/public.controller.js` (the
   hardened submission path) and `src/services/jobQueue.js` (the
   retry/failure-alert pattern) — those two files carry most of what makes
   this capstone "Medium–Hard" rather than plain CRUD.
2. **Run it yourself**, both the quick-start (SQLite) and the full Docker
   path, and watch it actually work end-to-end on your machine, not just
   trust that it worked on the machine that built it.
3. **Fill in `EVIDENCE.md`'s remaining items** — the ones marked
   `TODO (fill in yourself)` need proof from *your* running instance
   (particularly anything that needs a browser, like the cross-origin
   widget actually rendering on the test-site page — that can't be proven
   from a terminal).
4. **Push it to your own public repo incrementally**, per Section 11 — a
   single "final version" commit doesn't match what this log describes.
5. **Update this log** with your own notes as you go: what you changed,
   what you didn't understand at first and had to dig into, anything you
   ripped out or rewrote. That's the part of this file only you can write.
